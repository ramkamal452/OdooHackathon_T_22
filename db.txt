Below is a **full explanation of every table and every field** in that schema, with the design intent behind each one.

---

# 1) `USERS`

This is the master identity table for everyone in the platform.

## Purpose

Stores:

* admins
* instructors
* learners

This is the root user table used by almost every other table.

## Fields

### `id` PK

Unique primary key for each user.

### `full_name`

The user’s display name.

### `email` UK

Unique email address. Used for login, invitations, communication, and identity.

### `password_hash`

Hashed password value.
If you use Django auth fully, this maps to Django’s stored password field.

### `role_code`

Numeric representation of role.

Suggested values:

* `1 = admin`
* `2 = instructor`
* `3 = learner`

Why numeric:

* smaller storage
* faster comparisons
* cleaner indexing than text role names

### `is_active`

Whether the account is active or disabled.

### `created_at`

When the user was created.

### `updated_at`

When the user record was last changed.

### `last_login_at`

Useful for analytics, security, and admin visibility.

# 2) `ASSETS`

This table stores metadata for files stored in **Amazon S3**.

## Purpose

Do **not** store images/videos/PDFs in MySQL.
Store only metadata in DB, and actual files in S3.

Used for:

* thumbnails
* videos
* PDFs
* captions
* badge icons
* downloadable resources

## Fields

### `id` PK

Unique asset ID.

### `storage_provider`

Which storage system is used.

Suggested values:

* `1 = Amazon S3`
* `2 = CloudFront-backed S3`
* `3 = local dev storage`

### `bucket_name`

S3 bucket name.

### `object_key` UK

The exact S3 object path/key, for example:
`courses/python/intro/video1.mp4`

Unique because each object path should identify one object.

### `file_name`

Human-readable original file name.

### `mime_type`

Type of file, such as:

* `image/png`
* `video/mp4`
* `application/pdf`

### `file_size_bytes`

Size of the file in bytes.

### `checksum_sha256`

Optional integrity hash. Useful for deduplication or verification.

### `width`

For images/video thumbnails.

### `height`

For images/video thumbnails.

### `duration_seconds`

For audio/video assets.

### `etag`

S3-style file change reference or hash-like metadata.

### `is_public`

Whether the file can be served publicly without signed URLs.

### `uploaded_by` FK

User who uploaded the file.

### `created_at`

When asset metadata was created.

# 3) `CONTENT_ENTITIES`

This is the **core flexible content table** of the whole platform.

## Purpose

Stores all high-level content objects in one place.

Examples:

* course
* module
* lesson
* video item
* quiz item
* article item
* resource item
* assignment later

This is the key table that makes the design flexible.

## Fields

### `id` PK

Unique ID for each content object.

### `entity_type`

Tells what kind of thing this record is.

Suggested values:

* `1 = course`
* `2 = module`
* `3 = lesson`
* `4 = video`
* `5 = quiz`
* `6 = article`
* `7 = resource`
* `8 = assignment`

This is the heart of the polymorphic design.

### `title`

Main title of the content.

Examples:

* `Python Basics`
* `Module 1: Introduction`
* `Intro Video`
* `Quiz 1`

### `slug` UK

Readable unique identifier for URLs.

Examples:

* `python-basics`
* `intro-to-ai`

Usually important for:

* frontend routes
* SEO-friendly links
* clean public URLs

### `short_description`

Short summary for cards and listings.

### `description`

Longer detailed description.

### `owner_id` FK

Who created or owns the content.

Usually:

* instructor
* admin

### `status_code`

Publication state.

Suggested values:

* `1 = draft`
* `2 = published`
* `3 = archived`
* `4 = hidden`

### `visibility_code`

Controls who can see it.

Suggested values:

* `1 = private`
* `2 = invited_only`
* `3 = enrolled_only`
* `4 = public`

### `thumbnail_asset_id` FK

Optional thumbnail/image for this content entity.

### `estimated_duration_seconds`

Estimated time to complete/watch/read.

Useful for:

* course cards
* learner planning
* progress views

### `allow_standalone_enrollment`

Whether a user can enroll/access this item directly without it needing to sit under a course.

This supports your test case:

* standalone lesson
* standalone quiz
* standalone video

### `is_reusable`

Whether the same content can be reused under multiple parents.

Example:

* same quiz reused in two modules
* same lesson used in multiple courses

### `published_at`

Actual publish timestamp.

### `archived_at`

When it was archived.

### `created_at`

Creation timestamp.

### `updated_at`

Last update timestamp.

### `deleted_at`

Soft delete marker if you want recoverability.

# 4) `CONTENT_STRUCTURE`

This table defines the parent-child hierarchy of content.

## Purpose

This is what makes the schema flexible.

Examples:

* course -> module
* module -> lesson
* course -> video
* course -> quiz
* module -> video
* standalone lesson -> no row needed here

This table controls structure, sequence, preview rules, and unlock behavior.

## Fields

### `id` PK

Unique row ID.

### `parent_entity_id` FK

The container/parent.

Example:

* Course A

### `child_entity_id` FK

The child item inside that parent.

Example:

* Module B
* Quiz 1
* Intro Video

### `sort_order`

The order in which the child appears under the parent.

Examples:

* `1`
* `2`
* `3`

Important for course outline rendering.

### `is_required`

Whether completing this child is mandatory for parent completion.

### `is_preview`

Whether learner can access this child before enrollment/purchase.

Example:

* first lesson free preview

### `unlock_rule_code`

Type of unlocking behavior.

Suggested values:

* `1 = immediate`
* `2 = after_previous`
* `3 = after_prerequisite`
* `4 = scheduled`
* `5 = manual`

### `unlock_rule_config`

JSON config for detailed unlock logic.

Examples:

* unlock after date
* unlock after completing 80%
* unlock when previous child is passed

### `created_at`

Creation timestamp.

# 5) `ENTITY_STATS`

A summary table for precomputed stats.

## Purpose

Avoid expensive repeated calculations on large content trees.

Instead of recalculating counts every time, keep summary values here.

## Fields

### `entity_id` PK, FK

Same ID as corresponding content entity.

### `direct_child_count`

How many direct children this entity has.

Example:

* course has 8 direct items

### `required_child_count`

How many of those direct children are required.

### `total_duration_seconds`

Precomputed total duration.

Very useful for:

* course cards
* dashboard
* analytics

### `enrollment_count`

How many users enrolled.

### `completion_count`

How many finished.

### `average_rating`

Average review rating.

### `total_reviews`

Total review count.

### `total_points_awarded`

Total points issued from this entity or inside this entity.

### `updated_at`

When stats were refreshed.

# Relationship logic summary

## Core content model

`CONTENT_ENTITIES` stores all content objects.
`CONTENT_STRUCTURE` links them in parent-child trees.

That is what gives you:

* standalone lesson
* direct video under course
* direct quiz under module
* mixed content hierarchy

## S3 file model

`ASSETS` stores metadata only.
Actual binary files live in S3.

## Progress model

`ENTITY_PROGRESS` tracks learner activity at any content level.
`COURSE_MEMBERSHIPS` tracks course-level membership and invitation lifecycle.

## Quiz engine

* `QUIZ_CONTENTS`
* `QUIZ_QUESTIONS`
* `QUIZ_OPTIONS`
* `QUIZ_ATTEMPTS`
* `QUIZ_ATTEMPT_ANSWERS`
* `QUIZ_REWARD_RULES`

Together these fully support configurable quizzes and attempt-based points.

## Gamification model

* `USER_POINT_LEDGER`
* `BADGES`
* `USER_BADGES`

This handles points and badges in an auditable way.

---

# Why the design is strong

## Flexibility

A course can contain:

* module
* video
* article
* quiz
* resource

A module can also contain those.

A lesson can exist alone.

## Scalability

The main hot tables are narrow:

* `CONTENT_ENTITIES`
* `CONTENT_STRUCTURE`
* `ENTITY_PROGRESS`
* `COURSE_MEMBERSHIPS`

Heavy content is split into detail tables.

## Storage efficiency

Large files are in S3, not MySQL.

## CPU efficiency

The design supports optimization through:

* narrow hot tables
* numeric codes
* precomputed stats
* cache-friendly structure
* separate detail tables

---

# One important implementation note

In a real Django/MySQL system, you should also add:

* unique constraints
* composite indexes
* foreign key indexes
* check constraints where possible
* enum mapping constants in code

Because schema quality is not just tables and columns; it is also:

* indexes
* constraints
* migration safety
* query design
